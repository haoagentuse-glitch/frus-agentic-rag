## 0. 先讀這一節：所有「正確率」數字目前都作廢

裁判的系統提示詞對它說「REFERENCE 區塊包含這些文件的**全文**」，並要求
「參考資料沒有的具體事實一律給 0.0，不給部分分」。

實際上 `gold_excerpt` 寫死 `.limit(4)` 個片段、`max_chars=2500`：

| | 字元數 |
|---|---:|
| 模型看到的標準文件全文 | 312,252 |
| 裁判看到的 | 91,313（**29.2%**） |
| 最差的一題（lookup-01） | 80,123 → 2,694（**3.4%**） |

**模型從文件後 71% 正確作答，裁判依規則必須打 0。**

已修（`3f47f5b`）：參考區塊放寬到 60,000 字元、`.limit(200)`，覆蓋率
**29.2% → 94.8%**，截斷處標 `[TRUNCATED]`；評分規則改為「0.0 是**牴觸**證據，
準確但不完整給 0.6–0.9」。每輪多花約 $0.014。

驗證：拿 10 筆原本 0 分的重判（**仍用 200 字元的截斷預覽**），平均
**0.000 → 0.600**，沒有一筆仍是 0。

### 作廢清單

| 數字 | 狀態 |
|---|---|
| v1 那輪的正確率（0.414 / 0.386 / 0.343） | 作廢 |
| A/B/C 四個 variant 的正確率，含「B 是唯一單調遞增」的發現 | 作廢 |
| D2 = 0.276、D_base = 0.279、D4 = 0.204、D1 = 0.000 | 作廢 |
| 門檻 1 的 correctness 分量 | 作廢 |
| D0 表的 `correct` 欄位 | 作廢 |

### 仍然有效（確定性指標，不經模型）

語料統計、各層文件召回、路由 macro-F1、拒答次數與成因、成本（檢索次數／模型呼叫數）、
`score_distribution` 的交叉編碼器分數、證據片段覆蓋率、D6 的檢索失敗分類。
延遲數字**只有 Phoenix 關閉或縮減 payload 之後那幾輪**有效。

## 2. 已知問題（未解決，依嚴重度）

### 2.1 沒有任何機制檢查「證據是否支持主張」—— 最高優先

post-hoc 歸因把引用編號從生成任務移除了（見 3.1），但它掛上的是
**這條主張最像哪一段**，也就是**它是從哪一段寫出來的**。

我試過用分數門檻擋掉沒有根據的主張，量測後刪掉了（`8953d75`）。理由不是門檻沒調好，
是**工具不對**：29 條主張的最佳段落分數落在 0.285–8.953，中位 4.473，任何門檻都擋不到；
而且一條**過度延伸原文**的主張，跟原文的相似度反而更高——因為它就是從那裡改寫的。

所以現在的狀態是：

> **每條主張都會拿到引用。引用的意義是「出處」，不是「驗證」。**

要補這個缺口需要一個**蘊涵檢查**（claim 對 passage，NLI 式），那是一個階段，不是一個參數。

### 2.2 D 系列全部要重跑

三個原因疊在一起：

1. **裁判視窗**（第 0 節）——所有正確率作廢
2. **D1 被我做壞了**。我先前把提示詞改成「不要自己寫編號」，D1 只切換了
   `citation_mode` 旗標而提示詞沒跟著切回去，所以那一輪是「叫模型不要寫編號、
   然後閘門要求編號」。27/28 拒答是壞掉的組態，不是舊系統。
   已修（`e85e7bf`）：`synth_system(language)` 依模式選擇編號指示。
3. **D2 只存了 200 字元預覽、沒存評分理由**，所以 0 分無法區分是答錯還是評錯。
   已修（`398a129`）：存完整答案與評分理由，ablation 也存理由。

**D0 與 D6 不受影響**（不經裁判），結論見第 4 節。

### 2.3 B3 的糾正迴圈在門檻未設時不會觸發

`select.py::missing_hops` 靠 `score_keep_absolute` 判斷一個 hop 有沒有找到東西。
它預設是 `None`（絕對門檻不可用，見 4.2），所以回傳空陣列，**B3 目前等於 B2**。

`tests/test_graph_budget.py` 用 `FRUS_GRADER_MODE=llm` 固定成舊模式才還能覆蓋糾正路徑。

### 2.4 路由 macro-F1 0.4506，遠低於 0.80 門檻

規則式路由更差（0.2258），所以 SPEC 裡「不到 0.80 就退回規則式」的預案反而會讓結果變糟。
這是產品決策，尚未做。（此數字為確定性指標，**仍然有效**。）

### 2.5 句子過濾有沒有用，還不知道

`focus` 只改提示詞呈現的文字（`text_focus`），不改檢索結果與可引用單位，
所以它**不可能改變一則引用的意義**——這是刻意的隔離。

量過的：文字保留 63–74%、GPU 上 2–4 秒、CPU 上自動停用。
**沒量過的：對正確率有沒有幫助。** `C_focus_off` 那組配對實驗就是為了量它，
但那一輪被裁判問題毀了。

另外兩個參數是拍的、沒調過：`focus_max_sentences = 4`、`focus_context_sentences = 1`。

### 2.6 `timeline_search` 零測試覆蓋

gold set 裡沒有任何 timeline 題。三類該補的題型：高扇出多跳（10–14 份 anchor）、
有時間範圍的編年題、過寬而應拒答的題。

### 2.7 拒答會移除一個安全訊號

舊制下「模型寫了壞編號」會導致拒答。post-hoc 之後拒答只剩三條路徑：
沒有證據、沒有主張、閘門判定全部主張都無法引用。

門檻 3（不可回答題誤答）本來就沒過（2–3 筆），**下一輪必須確認它沒有變得更糟**。
這是用拒答率換正確率的交換，方向要靠量測確認，不能先宣稱它是淨賺。

### 2.8 WSL 記憶體未設定

主機 32GB，WSL 預設只拿 15.5GiB。建議 `.wslconfig` 設 `memory=24GB, swap=8GB`。

## 3. 已解決的

### 3.1 中文 40% 拒答 —— 引用編號改由程式產生

上一輪 350 runs：可回答題中 zh-TW 拒答 40.7%、en 12.0%。79 筆拒答中有 57 筆是
「有主張、每條都帶編號、但引用數 0」——編號不是檢索到的那些。

修法（`3a7ece1`，`agent/attribute.py`）：模型只寫主張，由已經在排序的交叉編碼器
把每條主張對每份已接受段落評分，**程式**掛上編號。模型從此不可能引用到沒被檢索的東西，
因為它根本不指名任何東西。`citation_mode` 預設 `post_hoc`，設 `model` 可切回舊行為。
2-step 基線也套用，否則消融會變成在比引用方案而不是比圖。

**引用閘門改為部分接受**：8 條主張裡 1 條壞掉只丟那一條，只有全部無法引用時才拒答。
無法引用的主張會從答案中移除。個別編號被拒的原因走 `reasons` 通道，
trace 仍看得到是「編造」還是「未被接受」。

實測（真實語料）：先前 4 次 smoke 有 2 次拒答且完全照語言分，改完之後
**4/4 全部作答**，主張全數掛上引用、0 條被丟棄、閘門 0 錯誤。

### 3.2 「文件命中」不等於「證據命中」—— 指標已建立，我的假設被推翻

我曾把「引用到標準文件卻仍被判 0 分」的 15 題歸因於片段切割。
`scripts/evidence_coverage.py` 量出來：

| 指標 | 數值 |
|---|---:|
| 文件層級召回（進入合成視窗） | 0.9667 |
| **證據片段層級召回** | **0.9667** |
| 文件命中但證據片段沒進來 | **0** |
| 每份標準文件平均片段數 | 5.7 |

**假設被推翻。** 文件確實是多片的，但最該進來的那一片，30 份中有 29 份都送到了模型面前。
片段切割不是成因。指標保留——它現在是量測過的不變量，而不是假設。

（注意：那 15 題的「判 0 分」本身也受第 0 節影響，所以「為什麼答錯」這個問題重開。）

### 3.3 LLM grader 移除，改為確定性分數過濾

兩個方向都失敗的紀錄：

| 版本 | 行為 | 結果 |
|---|---|---|
| 原始（點名保留） | schema `max_length=8`、視窗 10 片 | 砍掉 40% 文件含 15 份 gold；單 hop 時 2 片純粹被 schema 砍掉 |
| 反轉（點名拒絕） | 兩版 prompt、交集規則 | 4/4 smoke 全部零拒絕，完全空轉 |

改為 `retrieval/select.py::select_evidence`，B2/B3 的 LLM 預算從 4 降到 3。

### 3.4 Phoenix 把延遲灌水 4–19 倍

span payload 原本每題約 200KB，exporter 每批逾時 10 秒。同一題 B3：
**追蹤開 789s、關掉 42s**。已把上限降到 4000 / 500 字元 / 5 份文件
（`observability.py`，`PHOENIX_MAX_*` 可調回）。

### 3.5 映像檔：19.2 GB → 9.56 GB，Docker 總量 39 GB → 17.9 GB

成因不是「重複的 layer」而是**被遮蔽的 venv**：`jobshift:latest` 與本專案都把
virtualenv 放在 `/opt/venv`，本專案的 `uv sync` 覆寫了它，而 Docker layer 是疊加的。
映像因此帶著一套 6.4 GB 完全無法存取的 torch。

改以 `python:3.12-slim-bookworm` 為基底。不需要 CUDA 基底映像，torch wheel 自帶 runtime。
`jobshift:latest` 已刪除。Ollama 拆成 `Ollama/compose.yaml`，權重放在
external volume `ollama-models`（新機器要先 `docker volume create ollama-models`）。

### 3.6 裁判可切換供應商

`DEEPSEEK_API_KEY` 存在時走 DeepSeek，否則走 Gemini。理由是額度：Gemini 免費層
500/天，中途用完會把 195 筆判斷記成 0 分（已修為記 `None`）。
整套 D 系列在 DeepSeek v4-flash 上約 $0.05。

## 4. 判準稽核（16 個判斷點）

### 4.1 找到並修正的錯誤

| 判準 | 錯誤 | 提交 |
|---|---|---|
| 裁判參考視窗 | 提示詞宣稱全文，實際 29.2%，規則據此打 0 | `3f47f5b` |
| 門檻 1 | `any(recall, correctness)`，正確率跌 1.43pp 仍回報 pass=True，且不說 | `afa1e2c` |
| 門檻 4 | **從來沒有預登記門檻**，卻放在 `gates` 裡且 `pass` 未設——缺席被讀成通過 | `afa1e2c` |
| D0 欄位名 | `gold_in_top20` 存的是 `candidate_recall`，量在 k=50 | `afa1e2c` |
| `attribution_min_score` | 空轉且任何值都不可能有效 → 刪除 | `8953d75` |

**共同模式：不是計算錯誤，是標籤與行為脫節。** 每個數字單獨看都對，
問題在它被拿來回答的那個問題。

### 4.2 標準可疑但計算正確（要知道怎麼讀）

**`score_keep_absolute` 不要用。** 完整分佈（35 cases、1400 rows、119 gold）顯示
gold 的 p5 是 −3.17、非 gold 的 p95 是 +0.45，尾巴大幅重疊；保 100% gold 的地板是
−4.46，而它會留下 74.8%。**相對 margin 才是主控制項**：
`margin = top_score − 最深一份 gold 的分數`，p90 3.50、p95 3.96、**max 4.28**，
跨題型只差 1.4 個單位（絕對分數差 3.2）。故 `score_keep_margin = 4.3`。

**`citation_precision` 只在同一個引用方案內可比。** 它不是「引用得準不準」——
gold 每題只有 1–3 份、機器產生、未經史學覆核，引用一份真的相關但不在清單上的文件會被扣分。
它的工作是**讓「引用全部東西」變成有代價的**：recall 單獨看，最佳策略是把每份文件都掛上，
而 `attribution_top_k = 3` 讓那真的做得到。precision 是那個讓分母長大的制衡項。
換 `attribution_top_k` 會機械性改變分母，所以舊的模型自寫編號那幾輪跟 post-hoc **不能同表比較**。

**`claim_citation_coverage` 已失去意義。** 它量「有多少主張帶了引用編號」，
而 post-hoc 之後編號由程式掛上，會趨近 1.0 而沒有資訊。

**拒答在可回答題上一律記 0 分**，跟「牴觸證據」同分。裁判規則現在區分
「不完整」與「錯誤」，拒答沒有跟著區分。這是產品決策，可辯護，但要知道。

### 4.3 查過沒問題的

`_recall` / `_precision` 的空集合處理（回傳 `None` 不回傳 0）、門檻 2、門檻 3、
門檻 5 的邏輯、`abstention_precision` / `recall` 的分母、
`false_answer_on_unanswerable` 的定義、規則式路由的順序、`_filters` 的卷次／日期驗證、
引用閘門的阻斷條件、核心題目集的選擇與保真度曲線。

### D2 —— 唯一有實際效果的介入

| | 正確率 |
|---|---:|

## 6. 建議的下一步順序

1. **重跑 D2**（裁判已修、會存理由與完整答案）。這是唯一能分辨
   「檢索沒送到證據」與「模型用不了證據」的實驗，而且幾乎免費。
2. **重跑 D1**（提示詞已跟 `citation_mode` 綁定）。
3. 依 D2 的結果分支：生成模型是瓶頸 → 跑 D3；證據沒送到 → 回到檢索側，
   而 D6 說最大的一類是精確查詢（48%），先查 `head_search` 的權重設定。
4. 補 2.6 的三類題型。
5. 最後才做 B4 的正式比較（B3 對 B4，完整題庫，逐題配對）。

**縮減題目集用於迭代，完整題庫用於最終結論。** 10 題在 3.5× 加速下保留了
全集認定為決定性（>3pp）的**全部**配對順序，但絕對數值會偏移最多 7.29pp——
**它能說哪個設定比較好，不能當報告數字**。且它是在既有 20 種配置上選出來的，
屬於樣本內驗證。

### 昂貴的索引方法不要直接全量測

延遲切塊、脈絡化檢索、文件端擴充都要重建大量索引。先用固定的小型代表性語料篩選，
只讓勝出的 1–2 個方法重建完整索引。

**而且在 D2 重跑之前，這些一項都不要開始**——如果瓶頸在生成模型，它們的期望收益接近零。

## 7. 反覆出現的失效模式

這個專案至今出現過**七次**同一種故障：**元件安靜地失效，而儀器回報成功。**

1. 交叉編碼器因執行緒競爭從未真正執行，卻回報有跑
2. planner 捏造 volume_id，52% 子查詢回傳零筆而 `errors: []`
3. grader 把沒看過的證據當成拒絕
4. Ollama 停機期間寫下 42 筆假拒答
5. Phoenix 把延遲灌水 4–19 倍，看起來像 agent 慢
6. VM 上的 D0 寫出 0 位元組檔案並同步覆蓋好的那份
7. 裁判只看到 29.2% 的文件，卻被指示把視窗外的正確答案打 0

**所以新增任何階段時，trace 必須記錄它實際做了什麼，而不是它被呼叫了。**
現有的防護：`focus_active()` 回傳停用原因、`select_evidence` 在未設門檻時記下
`skipped` 與 `score_range`、fingerprint 問「有沒有真的跑」而不是「有沒有設定」、
judge 失敗記 `None` 不記 0、D2 存完整答案與評分理由。

**還有一個推論：一個看起來像防護、實際不可能觸發的東西，比沒有防護更糟。**
`attribution_min_score` 就是這樣被刪掉的——留著它會讓人以為有支持度檢查。
缺口要寫在程式碼裡（見 2.1），不要用假守衛蓋住。
